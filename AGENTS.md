# Zipy — agent guide

One agent a whole team shares, adapting to each person individually while acting on resources
the whole team owns. Built first for university student orgs. The invariant that holds the two
halves together: adaptation may change how the agent talks and how much it does on its own, and
it may never lower the bar on a consequential action. Per-member state is scored dimensions and
never stored text, and nothing derived from behaviour reaches the permission path.

Zipy owns the loop, the tool layer, the permissions, the memory and the traces; a chat workspace
(Discord today, Slack and others as plugins) is one surface onto it, and `apps/cli` is the other,
where the agent, its tools, providers and knowledge are configured. Tools reach the org's Google
Calendar, Drive, Notion and Zoom through one agent.

Read `docs/VISION.md` for the claim and what is deliberately not being built, `docs/ROADMAP.md`
for what is being built in what order, and `docs/ARCHITECTURE.md` for the layers, plugins, data
model, request lifecycle and invariants. Do not contradict them; propose an edit to the doc
instead.

## Commands

`just` is the entrypoint (`just` lists recipes). Install: https://just.systems.

```
just bootstrap          # first run: .env, hooks, dependencies
just doctor             # tools, secrets, and which services are up
just setup              # install every app (uv sync --locked)
just check              # the gate: check-python and check-website; CI and the hook run what changed
just check-python       # format, lint, layering, types, tests for every Python app
just check-website      # eslint and tsc for the website
just test integration   # tests against postgres and redis; needs ZIPY_TEST_DATABASE_URL, which they wipe
just fmt                # format in place
just lock               # re-resolve uv.lock after changing any pyproject.toml

just up [services]      # compose: postgres redis by default; langfuse prometheus grafana uptime-kuma
just down | logs        # stop the compose services, follow their logs
just migrate            # alembic upgrade head
just revision "msg"     # a migration autogenerated from engine/data/tables.py
just serve              # every enabled platform, the HTTP server, and the workers
just chat [--jsonl]     # talk to Zipy in the terminal through the local platform
just traces [id]        # the newest request traces, or one request's events
just eval [--case id]   # the eval cases against the configured model; not part of the gate
just data ...           # export | verify | review | curate | stats: the dataset from real runs
just train sft          # post-training over the curated set; needs a GPU and the gpu extra
just plugins            # every platform, provider and tool plugin, checked against zipy.toml
just mcp <tool>         # an MCP server's tool list against the tool's catalog; --write updates it
just config [table]     # the resolved configuration, secrets masked
just fernet-key         # a key for ZIPY_DATA__FERNET_KEY
just console            # the developer console (TUI): units, logs, chat, metrics; alias: just cli
just diagrams           # render every mermaid diagram in the docs; the hook runs it on doc changes
just web | web-build    # the website's dev server, its production build
just web-frames         # regenerate the website's logo animation from apps/cli/assets
just github [apply]     # branch rules and repo settings from .github: show the diff, or apply it
just release X.Y.Z      # a release branch with every version bumped; just tag after it merges
```

A change is not done until `just check` passes.

## Branches and pull requests

`main` takes no direct pushes; the rulesets in `.github/rulesets` enforce it on GitHub and the
pre-push hook refuses it locally. Work on a branch, open a pull request, squash merge. The one
required check is `CI`, which waits for every job in `ci.yml`; a new job goes in its `needs`
(`tests/test_repo.py` fails otherwise). Branch rules, repository settings and workflows change in
a pull request like code; `just github apply` applies the settings after merge. Never push to
`main`, force-push, move a tag, or run `just github apply` or `just tag` unless asked.
See [CONTRIBUTING.md](CONTRIBUTING.md) for releases and the full CI and CD table.

## Layout

One repo: a uv workspace of three Python apps, and the website. Language is never a folder.

```
apps/engine     the one process: platforms, api, workers, gateway, agent, tools, memory, llm,
                auth, data
apps/cli        the developer console; assets/ holds the logo animation exports
apps/training   datasets from real runs, the decisions about them, and post-training
apps/website    the landing page: Next.js, React, Tailwind, TypeScript; no blog
docs/           ROADMAP.md, ARCHITECTURE.md
evals/          the cases and fixtures just eval runs
tests/          repository wiring: workflows, branch rules, recipes, versions agree
.github/        workflows, rulesets, settings.json, CODEOWNERS, issue and pull request templates
deploy/         Dockerfile, compose.yml (+ prod overlay), postgres init
zipy.toml       every tunable: model roles, and one table per platform, provider and tool
```

Each Python app directory is its own package (`apps/engine` is `engine`) with its own
`pyproject.toml`, listed in `[tool.uv.workspace]` members. A new subpackage is added to that app's
`[tool.setuptools]` packages. The website has its own `package-lock.json`, installed with `npm ci`.

The logo animation has one source, the ASCII Motion exports in `apps/cli/assets`. The console
plays them; `apps/website/lib/cli-frames.ts` is generated from them by `just web-frames` and never
edited by hand.

## The dependency rule

Apps never import each other; the website imports nothing from the repo but its generated frames.
Inside the engine a package imports only packages below it, never a
sibling on its own row:

```
commands        the zipy command
evals           the cases in evals/, run over fixtures rather than providers
wiring          builds everything, runs platforms + api + workers in one event loop
platforms | api | workers
gateway         platform-neutral: org and role, rate limit, admin commands, confirmations
agent           orchestrator, prompt builder, classifier
memory | tools | llm | auth
data            postgres, pgvector, redis, the credential vault
telemetry       structlog, trace files, prometheus metrics, sentry
core            config, types, protocols, doubles
```

`scripts/check-deps.sh` runs the contracts in the root `pyproject.toml` under
`[tool.importlinter]`. Adding an edge means editing the contracts and `docs/ARCHITECTURE.md` in the
same change. On top of the layers:

- Only `engine.llm` imports litellm or langfuse. Only `engine.data` imports sqlalchemy, asyncpg,
  pgvector, redis, alembic or cryptography. The gateway and below import no web framework.
- No plugin imports a sibling plugin, and a library a plugin lists in `owns` is imported nowhere
  else. `apps/engine/tests/test_plugins.py` enforces both, so a new plugin needs no contract edit.
- Nothing below the gateway knows which platform a message came from beyond its name and
  capabilities. Memory never fetches from a provider: tools yield documents, workers ingest them.

## Plugins

Everything that varies is a plugin: a folder, a class, and a table in `zipy.toml`, discovered at
startup. A folder without a table or a table without a folder fails at startup.

```
platforms/<name>/platform.py       BasePlatform   [platforms.<name>]   a chat app Zipy lives on
auth/providers/<name>/provider.py  BaseProvider   [providers.<name>]   an account type orgs connect
tools/<name>/tool.py               BaseTool       [tools.<name>]       actions the model can call
```

Each declares `name` (folder and table), `owns` (libraries only it imports) and `settings_model`
(its own table keys, secrets included). Adding one never edits the gateway, agent, API or workers.

A tool gets its actions from a client written here (`github`, `notion`, `zoom`, `search`) or from an
MCP server (`calendar`, `drive`, `gmail`, `workspace`). A server-backed tool subclasses `RemoteTool`
and ships `catalog.json`, the server's own tools/list response plus the `exposed` list this
deployment offers; `zipy mcp <tool>` re-fetches it and says what changed. The server describes what
its tools take. It never says what they may do: `[tools.<name>.actions]` pins every exposed tool's
action type by hand, and a catalog entry nobody listed fails at startup rather than reaching the
model.
Use the `add-platform` and `add-tool` skills.

## The seams

Every replaceable dependency is a protocol in `engine/core/protocols.py` with a double in
`engine/core/doubles.py`: `ChatModel`, `Embedder`, `ConversationSource`, `Notifier`, `OrgStore`,
`WorkspaceStore`, `OrgContextStore`, `DocumentStore`, `CredentialStore`, `ToolConfigStore`,
`AuditLog`, `ConfirmationStore`, `RateLimiter`, `ProviderLimiter`, `JobQueue`, `TraceSink`,
`CollaborationStore`. A new one gets a protocol
and a double in the same change.

## Datasets and training

`apps/training` is the third app, and imports nothing else in the repo. It reads the same traces
the evals draft cases from: `data export` turns every `generation` event into an example,
`data verify` drops the malformed and the duplicates, `data review` judges them one at a time, and
`data curate` builds the training set from what was accepted. An example nobody reviewed is not
training data.

The decisions live in `apps/training/curation/decisions.jsonl`, committed: an export can be run
again, a judgment cannot. Each carries the fingerprint of the example it judged, so a changed
example is reported as stale rather than trained on. `train sft` needs a GPU and the `gpu` extra,
which the gate never installs.

## Inference tiers

Everything is OpenAI-compatible, so a tier is a `[models.chat]` change: a hosted provider,
llama.cpp via `just model`, or vLLM. `conditioning` on the role says what the endpoint accepts.
`memory/collaboration.py` holds one renderer per conditioning and `core/types` names which exist;
anything else is refused at boot. Text is the only one built and works on every tier. Adding a
prefix renderer is a renderer plus a serving tier, never a change to the gateway or the loop.

## Evals

`just eval` runs `docs/USER_STORIES.md` as cases in `evals/cases.toml`, against the configured
model, with every tool answering from `evals/fixtures.toml` instead of its provider. Correctness
(which actions ran, what the answer carried, whether a destructive call waited) and behaviour
(length, asked or acted, which tool first) are scored apart and never added. A `[[contrast]]` runs
one case at both ends of one collaboration dimension: correctness must hold, behaviour must move.
Renaming a story means renaming its case; a test holds the two files together. `just eval` is not
part of `just check`, because the gate needs no model.

`zipy eval-add <request-id> --id <case-id>` drafts a case from a real request's trace, with
`contains` left empty for the reviewer to fill in.

## Config

One `zipy.toml`, committed, shared by both apps; the engine reads every table but `[console]`,
the console only `[console]`. `ZIPY_<TABLE>__<KEY>` from the environment wins. `ZIPY_CONFIG_FILE`
points elsewhere; plugin secrets arrive as `ZIPY_<KIND>__<NAME>__<KEY>`. Models are roles
(`[models.chat]`, `[models.summary]`, `[models.embedding]`). Per-org overrides live in Postgres
(`org_tool_config`), never in the file. `config_version` is bumped only when a table changes shape
so an older file would be misread, with the upgrade steps in the release notes.

**Every tunable value goes in `zipy.toml`.** `.env` holds only secrets and per-machine URLs; a new
one goes in `.env.example` too. A new setting goes in `zipy.toml` at its default in the same
change. Reject a bad combination at load rather than clamping it at use.

## Rules

- Lints are the law (`[tool.ruff.lint]`, `mypy --strict` over both apps). Fix at the source rather
  than adding a `noqa`; a `noqa` names its rule and a reason.
- **org_id is the boundary.** A platform workspace is linked to an org; it is not the org. Every
  table has org_id, every repository method takes it, every log line and trace carries it. No
  query runs without one, except the workspace lookup and the workers' sweeps.
- **No platform, provider or tool is special.** No enum of them in code or the database, no
  `if platform == "discord"` outside that platform's folder. Names are strings validated against
  the plugins that exist.
- **Credentials never touch the model.** No token, key or header in a prompt, a tool result, a
  log line or a trace. Credentials are `SecretStr` until the client that sends them.
- **The config decides what is destructive, never the model.** Every action has a type in
  `zipy.toml`; destructive calls wait for a confirmation bound to the exact call, and expire.
- Raw API content (pages, files, transcripts, search results) only ever enters the model as a
  tool message or the recalled-context message, never the system prompt.
- Every tool execution writes an audit entry, success or failure. `audit_log` is never updated or
  deleted.
- Permissions are checked at execution, against the action type, not when the message arrives.
- Every model call, tool call, confirmation and reply emits a trace event through `TraceSink`, and
  counts in `Metrics`. Metric labels are plugin, role and outcome names, never an org id.
- One agent, many tools, and one level of delegation. `delegate` runs the same orchestrator loop on
  a subtask with a subset of the parent's tools and its own turn limit, and is never offered to a
  sub-agent. No specialist agent per integration, and no agent that exists before a request. The
  orchestrator is still the only thing that coordinates tools; it just may call itself once.
- No global mutable state. Per-request data travels in `RequestContext`.
- No silent fallbacks: a missing credential, template, key or table is an error that says what is
  missing. A platform without a capability (buttons, threads) degrades as the gateway says, not
  by guessing.
- Errors are `ZipyError` subclasses from `engine/core/types/errors.py`. No bare `Exception`
  raised, no `assert` for control flow outside tests.
- `uv.lock` is committed and every install is `--locked`. A schema change is an alembic migration
  in the same change.
- Comment style: see the `comment-style` skill. Plain ASCII, state what the code does, no
  rationale; the why belongs in the commit message.
- Commit messages: imperative subject at most 72 chars, body explains why.
